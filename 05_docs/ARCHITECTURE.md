# システム設計

各処理の連携、データとモデルの保存先、再実行時の制御をまとめる。学習・評価の条件と結果は[README](../README.md)・[EVALUATION.md](EVALUATION.md)、実行コマンドは[LOCAL_RUN.md](LOCAL_RUN.md)を参照。

## 1. システム構成

| 処理 | 実装 | 入出力・連携 |
|---|---|---|
| データ準備・日次登録 | `01_data/preparation`、`01_data/daily` | 元Excelから作成した日次CSVを検証し、取引明細と日次集計をPostgreSQLへ保存 |
| 品番選定・モデル学習 | `01_data/analysis`、`02_model/training` | DBの確定実績から品番選定・特徴量生成・学習を実行し、学習履歴とモデルをMLflowへ登録 |
| 週次予測・運用制御 | `02_model/weekly` | DBの実績とMLflowの登録モデルを使って予測し、結果をDBへ保存 |
| 週次評価 | `02_model/evaluation` | 保存済み予測と確定実績を照合し、評価結果をDBとMLflowへ記録 |
| 画面表示 | `03_app` | PostgreSQL・MLflowの保存結果を読み取り専用で表示 |

一連の実行制御は`02_model/weekly/replay.py`で行う。PostgreSQLは取引・予測・評価の結果、MLflowは学習条件・モデル・更新履歴を管理する。

## 2. データ・モデルの管理

| テーブル | 主キー・制約 | 主な内容 |
|---|---|---|
| `transactions` | `source_row` PK | 元データの行番号と対応付いた前処理後の取引明細 |
| `daily_sales` | `sales_date`, `stock_code` PK | 品番別の日次販売数量 |
| `daily_batches` | `batch_date` PK | 処理件数、CSVハッシュ、0件日の根拠、完了日時 |
| `operation_replays` | `replay_id` PK、`replay_key` UNIQUE | 運用再現の開始モデル、親Run、実行状態 |
| `weekly_forecast_runs` | `prediction_run_id` PK、運用ID・週 UNIQUE | 予測対象週、使用モデル、MLflow Run |
| `weekly_forecasts` | `prediction_run_id`, `stock_code` PK | 予測値、ベースライン、特徴量、確定実績 |
| `weekly_evaluations` | `prediction_run_id` PK/FK | MAE、WAPE、連続悪化回数、評価Run |

予測値は書き換えず、翌週の評価時に`weekly_forecasts`へ確定実績を追加する。`NULL`は未評価、`0`は販売数量0を表す。100品番の実績更新と週次評価の保存は1トランザクションで行う。

MLflowでは登録モデルのバージョンと再学習イベントを保持する。更新時には旧・新モデル、学習期間を記録し、DBの予測結果から使用モデルをたどれるようにする。

## 3. 週次運用の制御

月曜の処理は次の順序とする。

1. 前週の確定実績で予測を評価する。
2. LightGBMのWAPEがベースラインより2週連続で悪化した場合、確定済みデータで再学習し、MLflowへ新モデルを登録する。
3. 更新があれば新モデル、なければ従来モデルで当週の予測を保存する。
4. 月曜当日のCSVを登録する。

再学習判定はベースラインとの相対比較であり、モデル単独の精度悪化を必ずしも検知できない。

予測には直前の日曜までの実績を使うため、月曜当日の取り込みは予測後に行う。8月1日は前週評価を行わず、10月3日は最終評価のみ行う。

## 4. データ整合性・再実行制御

- **時点整合性：** 対象100品番は2011年5月29日までの実績で選定し固定する。学習には、その時点で予測対象の7日間すべての実績が確定しているデータのみを使用する。予測・評価の新規実行前にDBの最大実績日を確認し、未来の実績があれば停止する。
- **欠損の区別：** CSVがない日を販売0件とはみなさない。元Excelで取引0件と確認できた日だけ空CSVを作成し、確認結果とハッシュを記録する。評価前には対象7日間の取り込み状況を確認する。2010年12月27日〜2011年1月2日の共通空白期間を含むデータは学習・評価から除外する。
- **日次登録：** 登録済みの日付はCSVハッシュを比較し、一致すれば省略、不一致なら停止する。
- **週次予測・評価：** 運用IDは一連の運用再現、予測IDは各週の予測を識別する。一意制約によって重複登録を防ぎ、評価結果はまとめて保存する。
- **中断再開：** PostgreSQLとMLflowの保存済み結果を確認し、未完了の処理から再開する。MLflowはイベントキーで登録済みRun・モデルを再利用する。同時実行はDBのセッションロックで防止する。モデル更新や予測保存の途中停止については結合テストで確認した。
