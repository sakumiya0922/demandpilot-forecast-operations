# 【旧方式の記録】04：学習データの作成・時系列検証・モデル保存

> **履歴資料です。** 以下の`python -m training.train`は削除済みの旧コマンドです。現在の運用再現は[LOCAL_RUN.md](LOCAL_RUN.md)にある`python -m training.weekly_operations`を使用してください。旧評価値も現行方式の結果ではありません。

このフォルダは、初回の学習と、必要に応じた手動再学習で使う。毎週の予測は [step05](step05_weekly.md)、全体の準備手順は [トップREADME](../README.md) を参照する。

## 学習データを作る

```sh
docker compose run --rm pipeline python -m training.training_data \
  --start 2010-12-01 --end 2011-05-31
```

指定期間の取り込み完了が前提である。既定の出力先は `01_data/storage/training/weekly_training.csv`。
既存ファイルは上書きせず、再作成時は `--output 01_data/storage/training/weekly_training_check.csv` など別名を指定する。

固定100品番の日次カレンダーを作り、商品別の販売記録なしを0で補完する。
共通の不明期間2010-12-27〜2011-01-02は0にせず不明値として扱い、そこを含む履歴・正解は除外する。
カレンダーの週を詰めて、不明期間の前後を隣接させることはしない。
期間端の記録は確認するが、途中の全日について取り込み完了を自動判定する仕組みではない。

| 列 | 意味 |
|---|---|
| stock_code | 固定対象の商品コード。学習時はカテゴリ |
| forecast_origin | 日曜終了時点の予測基準日 |
| history_start | 28日履歴の先頭日 |
| target_start / target_end | 翌月曜〜日曜 |
| sales_sum_7 | 基準日を含む過去7日の販売数量合計 |
| sales_sum_28 | 基準日を含む過去28日の販売数量合計 |
| sales_std_28 | 過去28日の日次数量の標本標準偏差 |
| month | 予測基準日の月 |
| target | 翌7日間の実績合計。正解専用で特徴量には含めない |

記録した学習CSVは100品番×17基準日＝1,700行である。

| 期間の種類 | 記録した期間 |
|---|---|
| DBから読み出す指定期間 | 2010-12-01〜2011-05-31 |
| 実際の学習サンプルの基準日 | 2011-01-30〜2011-05-22 |
| 使用した特徴量の履歴開始 | 2011-01-03 |
| 学習サンプルの正解期間 | 2011-01-31〜2011-05-29 |

半年分を登録していても、履歴不足・不明期間・正解期間の条件により、商品ごとの週次サンプルは17件である。
元の読み出し指定期間は現モデルのconditions.jsonには未保存であり、画面では学習CSVに記録された実際の基準日範囲を表示す。

## 時系列で検証して学習する

```sh
docker compose run --rm pipeline python -m training.train
```

新しいCSVなら `--csv`、固定品番一覧は `--products`、記録先は `--tracking-dir` で指定できる。
毎回新しいMLflow実行を作り、既存モデルを自動的に切り替えない。

`TimeSeriesSplit`を週の基準日に適用し、同じ週の100商品をまとめて分割する。
学習ラベルの最終日が最初の検証基準日を超えないことを検査する。

| 分割 | 学習基準日 | 学習ラベル最終日 | 検証基準日 | 検証ラベル最終日 |
|---|---|---|---|---|
| 1 | 2011-01-30〜03-20 | 2011-03-27 | 2011-03-27〜04-10 | 2011-04-17 |
| 2 | 2011-01-30〜04-10 | 2011-04-17 | 2011-04-17〜05-01 | 2011-05-08 |
| 3 | 2011-01-30〜05-01 | 2011-05-08 | 2011-05-08〜05-22 | 2011-05-29 |

モデルは各分割の学習期間で固定し、各検証基準日までに観測した販売実績を特徴量へ使う。
固定パラメータのLightGBMと過去7日合計を比較し、探索・早期終了・結果による反復数変更は行わない。

| 指標 | LightGBM | ベースライン |
|---|---:|---:|
| 全検証900行のWAPE | 59.19% | 73.96% |
| 全検証900行のMAE | 173.69 | 217.04 |

100品番の選定に12月〜5月の情報を使っているため、この検証は探索的な比較である。完全に未知の最終評価とは呼ばない。
最終モデルは全17週で再学習する。`validation_*`は分割ごとの評価モデルの指標、`final_refit_train_*`は最終モデルの学習内指標であり、用途が異なる。
最終モデルを過去の検証行に当て直した値を検証精度とは呼ばない。

## MLflowに残す情報

| 保存物 | 内容 |
|---|---|
| 01_data/storage/training.csv・target_products.csv | 学習に使用したファイルのコピー |
| source | 学習・加工コード、依存設定、Dockerfile、商品選定SQL |
| conditions.json | 実行ID、モデルURI、パラメータ、分割、商品・特徴量一覧、Python・ライブラリ版、ハッシュ |
| evaluation | 検証の予測・正解・特徴量・商品別指標 |
| evaluation_models | 分割ごとの評価モデル |
| 保存モデル | 全17週で学習した最終LightGBMモデル |

```sh
docker compose up -d --build mlflow
```

http://localhost:5001 で実験 `demandpilot-v2` を開く。
現在の学習実行IDは `f66ae46e04604b0589d1ec8d38d3b378`、モデルURIは `models:/m-c2da0c5b99ee4065b56ba3acbcac8c36` である。
別環境で学習し直すとIDは変わるため、予測コマンドにはその環境で出力されたIDを指定する。

管理DBは `02_model/mlflow/mlflow.db`、成果物は `02_model/mlflow/artifacts/`。このフォルダ全体を保持する。
Docker内では共通の絶対パス `/app/02_model/mlflow/` を使う。ホストPythonから直接参照する場合はパスの違いに注意する。

再現にはコードだけでなく、学習CSV・商品一覧・学習条件・環境・保存モデルの対応が必要である。
テストと現在の確認状況は [トップREADME](../README.md#テストと確認状況) を参照する。
